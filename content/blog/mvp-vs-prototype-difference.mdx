When launching a new digital venture in Kenya, you will frequently encounter two terms used interchangeably: **Prototype** and **MVP (Minimum Viable Product)**.

While both are early-stage artifacts used to turn an idea into reality, they serve fundamentally different business objectives, require very different engineering investments, and deliver different outcomes.

Confusing a prototype for an MVP can lead to launching non-functional software to real customers—or spending months building a full backend when a simple visual prototype would have answered your early questions.

In this guide, we break down the exact differences so you choose the right approach for your startup.

---

## 1. Quick Summary

> **A Prototype tests visual appeal and user journeys.** It is a visual simulation with mock data.  
> **An MVP tests commercial demand and real user behavior.** It is functional software running on a live database and processing real transactions.

---

## 2. What Is a Prototype?

A prototype is a **visual or interactive model** of a software product. It demonstrates how the application will look and feel, but it does not connect to a live backend database, real user authentication, or payment gateways.

### When to Build a Prototype:
- Pitching an early-stage concept to angel investors or startup accelerators.
- Conducting initial user interface (UI/UX) usability testing with test subjects.
- Visualizing complex multi-step workflows before committing engineering budget.

### Key Characteristics:
- Built with design tools (Figma, Adobe XD) or lightweight front-end mockups.
- Uses static, hard-coded placeholder data.
- Built in 1 to 2 weeks at minimal cost.
- Cannot process live Safaricom M-Pesa payments or save real user records.

---

## 3. What Is a Minimum Viable Product (MVP)?

An MVP is a **fully functional, production-ready software product** containing only the essential features needed to solve the core problem for early adopters.

### When to Build an MVP:
- Onboarding real, paying customers to validate market willingness to pay.
- Collecting real usage analytics, error logs, and user behavioral feedback.
- Automating a business operation or replacing manual Excel spreadsheets.
- Establishing a scalable technical foundation for long-term growth.

### Key Characteristics:
- Built with production technologies (Next.js, TypeScript, PostgreSQL, Linux VPS).
- Connected to live payment systems (Lipa na M-Pesa STK Push callbacks).
- Real user authentication, session security, and role-based permissions (RBAC).
- Built in 4 to 8 weeks with complete data persistence and error logging.

## 4. Side-by-Side Comparison

| Dimension | Prototype | Minimum Viable Product (MVP) | Full Mature Product |
| :--- | :--- | :--- | :--- |
| **Primary Question** | "Does this flow make sense visually?" | "Will customers actually use & pay for this?" | "How do we dominate market share & scale?" |
| **Backend & Database** | None (static / mocked) | Live PostgreSQL / REST APIs | Distributed database, read replicas & cache |
| **Payment Integration** | Mocked button | Live Safaricom M-Pesa Daraja 2.0 | Multi-currency, automated subscriptions |
| **User Access** | Clickable link in Figma | Live public domain (HTTPS / SSL) | Multi-region, SSO & SAML enterprise auth |
| **Build Time** | 1 to 2 weeks | 4 to 8 weeks | 6 to 18+ months ongoing |
| **Cost** | Lowest | Moderate & scoped | High ongoing capital investment |
